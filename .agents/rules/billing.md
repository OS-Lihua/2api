# Billing Rules

Mandatory conventions for quota, pricing, pre-consume, settlement, refund, and usage-quantity code in the Go backend. `AGENTS.md` defines when a task touches billing (see **Billing rules (mandatory read gate)**); any task that matches MUST read this whole file before planning, coding, or reviewing. Tasks that match none of those triggers may skip it. Rules use the same MUST / Do NOT wording as `AGENTS.md` and carry the same weight.

**Billing expression system:** When working on tiered/dynamic billing (expression-based pricing), MUST read `pkg/billingexpr/expr.md` first. It documents the design philosophy, expression language, full architecture, token normalization rules, quota conversion, and expression versioning. All billing expression changes must follow that document.

**Built-in model pricing:** New built-in model prices MUST be defined as self-contained billing expressions in `setting/billing_setting/builtin_billing.go`, using real USD per million tokens. Do not add new built-in prices to the legacy model/completion/cache ratio tables. Preserve explicit administrator pricing overrides. Existing legacy prices are migrated only when explicitly requested. Verify published prices and cover applicable context-length thresholds and cache categories.

**Fixed-point money:** Amounts that carry a currency (wallet balances, ledger entries, sale and purchase prices, attempt costs, exchange-rate conversions) MUST use `pkg/money`. It replaces `common/quota_math.go` for these amounts; `common/quota_math.go` stays only for the legacy `int` quota paths until they are removed, and new code MUST NOT convert between the two.

- A stored amount is `money.Amount`: `int64` in 10⁻⁹ units of the currency plus an ISO 4217 code. Embed it with `gorm:"embedded;embeddedPrefix:<name>_"` to get a `bigint` and a `char(3)` column. Do not store amounts as `float`, `numeric`, or `int` quota.
- Calculate with `money.Value`: `Add`, `Sub`, `MulQuantity`, `MulUnitPrice`, and `Convert` with a `money.Rate`. Decimal inputs stay exact; repeating quotients remain rational until the write boundary. Do not use rounded decimal division for an intermediate amount, route amounts through `float64`, or build `money.Amount` from `decimal.IntPart()` or a bare cast.
- Do not round during calculation. Round only when writing: `Value.Receivable` rounds a user charge up to 10⁻⁹; `Value.Credit` rounds a user credit, such as a top-up converted from another currency, down to 10⁻⁹; `Value.Cost` rounds a purchase cost to the nearest 10⁻⁹, halves away from zero, so costs reconcile with provider invoices without drifting in one direction.
- Every operation returns `money.ErrOverflow` outside the `int64` range of 10⁻⁹ units and `money.ErrCurrencyMismatch` for different currencies. Reject the operation on these errors; never clamp, saturate, or truncate. Converting to another currency requires an explicit `money.Rate`.
- On PostgreSQL, `SUM` of an amount column returns `numeric`; scan it into `decimal.Decimal` and sum one currency at a time.

**Wallets and ledger entries:** The `wallets` and `ledger_entries` tables in the primary database are the only source of amounts. Accounts are a user wallet and a user receivable account (one of each per user, in `SETTLEMENT_CURRENCY`), platform revenue (one per currency), and a Provider payable (per Provider and currency).

- Change a balance only through `model.PostLedgerEntries`, `model.TopUpWallet`, or `model.ReverseLedgerEntry`. They lock each wallet with `lockForUpdate` in ID order and write the entries and balances in one transaction. Never update `wallets.balance_nanos` directly.
- Ledger entries are append-only: a database trigger rejects `UPDATE`, `DELETE`, and `TRUNCATE`. Correct a mistake with a reversal entry; an entry is reversed at most once and a reversal cannot be reversed.
- Each entry is non-zero and its sign must match its type and account: on a user wallet, top-up, pre-consume release, refund, and opening balance are positive, pre-consume, charge, and repayment are negative, and an adjustment may be either; on platform revenue and Provider payable accounts, charge is positive and refund negative. On user receivable accounts, charge creates positive unpaid debt and repayment reduces it. A reversal has the opposite sign. Repayment pairs and receivable entries cannot be reversed individually.
- Every user-wallet posting locks the corresponding receivable account in the same ID order. After the entire posting batch, spendable funds first repay outstanding debt through paired negative repayment entries on the wallet and receivable accounts. This applies to all credits, including top-ups, refunds, positive adjustments, opening balances, reversals, and reservation releases. Repayment never recognizes revenue again; it preserves the original credit's source amount and FX entry and identifies the funding credit. Repayments retain the original debt's request ID and pay the oldest unpaid request first. Unpaid debt keeps requests paused; a partial credit cannot restore dispatch.
- A posting that would make a user wallet negative fails with `model.ErrInsufficientWalletBalance`. Use `IdempotencyKey` for postings that must happen once, such as one pre-consume per request or one credit per payment reference.
- A top-up in another currency records the source amount and the exchange rate on the entry and credits the converted amount rounded down with `Value.Credit`.
- The `wallet_reconcile` system task checks that every balance equals the sum of its entries on the interval in `WALLET_RECONCILE_INTERVAL_MINUTES` (default 60), measured on `pkg/clock`. A mismatch fails the run and notifies the root user.
- Until the data migration command moves legacy balances into opening-balance entries, the `int` quota paths do not post to the ledger; do not mirror quota changes into wallets.
- The safety invariants below still apply: bound every billing multiplier before it reaches a calculation, and never let arithmetic or input produce a credit.

**ModelOffering gateway billing:**

- A resolved ModelOffering uses the money lifecycle. A disabled or unauthorized offering must not fall through to legacy relay billing. Credential validity, user status, expiry, IP restrictions, and model authorization still apply; legacy `int` quota is not a wallet balance.
- Freeze the sale price version and original expression at request start. Freeze the purchase price version and accounting FX at attempt start. Settlement and recovery use these snapshots, never the current configuration.
- Evaluate currency expressions with `billingexpr.RunMoneyExpr`, preserving decimal literals and numeric request probes. Detect referenced token variables with `MoneyUsedVars`; the legacy floating-point optimizer can discard a different branch for precise decimal comparisons. Normalize token categories before evaluation; use exact `TokenQuantities` for fractional cache normalization. Group discounts come from the stored decimal configuration, not the legacy floating-point ratio cache.
- Reservation uses estimated input plus the offering's recent mean output. The mean takes the latest 1000 successful requests in the preceding seven days and rounds the quantity up. With no history, use 1024 output tokens. Bound this estimate by the requested output limit and effective Model/Channel limit, then apply the validated choice count.
- `ReserveGateway` and `SettleGateway` compose the existing ledger posting primitive within the billing lifecycle transaction. They must retain its account locking order, entry validation, append-only history, and balance reconciliation. They must never write balances directly. An explicit free price still has a lifecycle row and records, without zero-valued ledger entries.
- A request has one reservation and one finalized settlement intent. Replays reuse the intent and idempotency keys. Settlement releases the reservation, charges the user, recognizes platform revenue, and posts each attempt's cost to the Provider payable account in its original currency. A shortfall preserves the complete receivable, recognizes its full revenue once, collects only available funds, and posts the unpaid difference to the user's receivable account. Subsequent credits repay existing debt before producing spendable funds; requests remain paused until all debt is paid. Released reservations also pay older debt before a concurrent request's new charge.
- Request and attempt records belong in the log database. The primary billing row retains the settlement intent and delivery outbox so log database failures cannot cause another charge. Recovery retries prepared settlements and unpublished finalized records; it must not refund a potentially active reservation solely because time elapsed.
- No-output failures release the full reservation. A fixed request price is charged only on success. Preserve the distinction between an explicit upstream zero and missing usage; mark local estimates as estimated. Route diagnostics and purchase details are administrator-only.

**Billing safety invariants:** Quota/billing code MUST never produce a negative charge (a credit) from arithmetic overflow or unvalidated input. Apply defense in depth:

- Every user-controlled quantity that becomes a billing multiplier (image `n`, video `seconds`/`duration`, resolution/quality ratios, batch counts) MUST be bounded before it reaches quota calculation. Reject out-of-range values at request validation with a 400. Existing bounds: `dto.MaxImageN` for image generation count, `relaycommon.MaxTaskDurationSeconds` for task video duration, `maxTokensLimit` (`relay/helper/valid_request.go`) for `max_tokens`-family fields on every relay format (OpenAI, Claude, Gemini, Responses). Reuse these constants instead of introducing new ad hoc limits for the same concepts. When adding a new relay format or request DTO, bound its max-tokens and count fields in its validator from day one.
- Watch for validation bypass paths: passthrough fields (e.g. `Extra["parameters"]`), task `metadata` maps, and multipart form fields can carry the same quantities around the standard DTO validation. Any adaptor that reads a multiplier from such a path must enforce the same bound (or clamp) locally. Task plugins validate their own requests: the host bounds every usage fact a plugin returns before quota calculation and does not interpret request members. A plugin MUST derive its facts from the request it sends upstream, including values merged from `metadata` or other passthrough maps, and MUST bound any request quantity it turns into a token or credit fact; the host caps `second` and `count` facts but only saturates `token` and `credit` facts at the int32 quota boundary. A plugin that forwards a duration of -1 (the vendor picks the length) must reserve the model's longest duration and settle on the usage the vendor reports.
- Durations parsed from media metadata are user/upstream-controlled too: audio file headers (transcription token counting, TTS response duration) and upstream deduction numbers (e.g. Kling `FinalUnitDeduction`) can claim absurd values. Convert them with saturation before they become token counts.
- Never convert a computed quota or token count to `int` with a bare cast like `int(float64(quota) * ratio)`, `int(math.Round(...))` on unbounded input, or `int(decimal.IntPart())`. All quota rounding/conversion is centralized in `common/quota_math.go`; use those helpers: `common.QuotaFromFloat` (truncating) for float products, `common.QuotaRound` (half-away-from-zero) where rounding is intended, and `common.QuotaFromDecimal` for decimal products. `billingexpr.QuotaRound` delegates to `common.QuotaRound`. Do not reintroduce local conversion helpers or bare casts. Single-request saturation stays at the int32 boundary so batch accumulation cannot approach 64-bit wraparound; wallet/top-up conversion uses `common.WalletQuotaFromDecimalStrict` with the JavaScript-safe `common.MaxWalletQuota` boundary. Every clamp/NaN fallback is logged via `common.SysError`.
- Saturation events are also audited: each helper has a `*Checked` variant (`common.QuotaFromFloatChecked` / `QuotaRoundChecked` / `QuotaFromDecimalChecked`) that additionally returns a `*common.QuotaClamp` when clamping occurred. Billing paths that compute a charge capture that clamp onto `relayInfo.QuotaClamp` (or thread it into task settlement) and, right before writing the consume/task log, call `attachQuotaSaturation` (in `service/log_info_generate.go`) which nests the marker under the log's `other.admin_info.quota_saturation` and emits a request-correlated `logger.LogWarn`. Nesting under `admin_info` makes it admin-only for free (non-admin log views strip `admin_info`). When adding a new billing path, use the `*Checked` variant and surface the clamp the same way so the anomaly stays auditable in both the admin log UI and backend logs.
- Multiplier maps go through `types.PriceData.AddOtherRatio`, which rejects non-positive, NaN, and +Inf ratios. Do not write to `PriceData.OtherRatios` directly, and do not weaken these guards.
- Pre-consume (预扣费) and settle (结算/差额) must both be safe: a saturated oversized quota must fail pre-consume with insufficient-quota, never silently wrap. When adding a new billing path (new relay format, new task platform, new adjustment hook), trace the full chain — validation → EstimateBilling/OtherRatios → quota conversion → pre-consume → settle/refund — and confirm each step preserves these invariants.
- Fields parsed into unsigned types (`*uint`) accept huge positive JSON numbers (e.g. `18446744073686646784`, a wrapped negative); a `>= 0` check is not sufficient, an upper bound is mandatory.
- Regression tests for these invariants belong with the boundary they protect (request validators, converter helpers). See `relay/helper/openai_image_request_test.go`, `relay/common/relay_utils_test.go`, and `common/quota_math_test.go` for the expected style.

**Upstream image quantity settlement:** The billable image count may be lowered or raised from the upstream response only through `RelayInfo.UpdateImageCount` on the HTTP image relay, or through the `image_count` usage fact a task plugin returns on completion; a zero or out-of-range count leaves the reserved request quantity in place. Derive the count from image payloads, never from JSON structure:

- Do NOT count `data` with gjson `data.#`, `len(data)`, or any element count. Providers behind OpenAI-compatible channels return non-standard shapes: `data` as a single object, one image split into a `url` entry and a `b64_json` entry, or entries carrying only `revised_prompt`.
- An object-shaped `data` is one image when it has a non-empty `url` or `b64_json`, otherwise zero. For arrays the count is `max(entries with non-empty url, entries with non-empty b64_json)`: a standard response uses one `response_format` so this equals the entry count, a split image bills once, and payload-less entries bill nothing. The reference implementation is `openaiImageResponseCount` in `relay/channel/openai/relay_image.go`; reuse it (or the same rule) for any channel that forwards or rebuilds OpenAI-format image responses. The xAI adaptor already inherits it through `OpenaiImageHandler`.
- When an OpenAI-format JSON body is re-emitted as SSE, forward one `image_generation.completed` event per image payload using the same shape handling (object → one event, payload-less entries dropped). The client must never receive only `[DONE]` while being charged for images.
- Real SSE streams count `image_generation.completed` / `image_edit.completed` events and only trust a lower count when upstream finished the stream (`done` / `eof`); a client abort must not reduce the charge below the requested quantity.
- Ali (Bailian) image models are served by the `alibaba` task plugin through the `openai_image` host protocol. Its `imageUsage` reads `usage.image_count`, then `usage.output_image_count` (Qwen-Image-3.0), and otherwise counts image payloads flattened across every `choices[].message.content[]` entry and `results[]`; payload-less parts bill nothing, and a fractional, negative, oversized, or payload-inconsistent upstream count keeps the reserved request quantity. Any other channel with its own usage field applies the same order: trust the bounded upstream count first, then count payloads. Channels that rebuild responses from typed structs count the typed slice; none of them may read `data.#`.
- Regression cases for object, split, and payload-less shapes belong in `relay/channel/openai/image_stream_test.go` (fixed-price, tiered-expression, and JSON-as-SSE forwarding tables). Extend those tables instead of adding new files.
